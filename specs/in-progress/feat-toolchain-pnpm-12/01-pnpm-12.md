# Phase 1 — Move the workspace and CI to pnpm 12.4.1, correcting the rationale it falsifies ⬜

> Spec: [00-overview.md](00-overview.md) · **Status:** Not started

**Goal:** the workspace, every spec worktree and CI all install on pnpm 12.4.1,
and no live comment still claims pnpm is what sets this repo's Node floor.

## Tasks

- [ ] Set `packageManager` to `pnpm@12.4.1` in the root `package.json`.
- [ ] Install with pnpm 12 and commit whatever `pnpm-lock.yaml` it writes.
      **Record the resulting `lockfileVersion` in this file's Notes; do not
      assert an expected one** — it is currently `9.0` and pnpm 12 may or may not
      bump it.
- [ ] Prove `pnpm install --frozen-lockfile` succeeds against the committed
      lockfile from a clean checkout with no `node_modules`. This is the exact
      command `specs/.core/env.config.json` → `setup` runs in every spec
      worktree, so a failure breaks `/spec-start` for every spec at once.
- [ ] Prove `pnpm/action-setup@v6` in `.github/workflows/ci.yml` provisions
      pnpm 12. **This is the one untested risk in the upgrade**: the action reads
      `packageManager` and installs from npm, and pnpm 12 ships an `install.js`
      shim that fetches a platform-specific native binary rather than the
      JavaScript CLI v11 shipped. If v6 cannot, the options are pinning the
      action to a version that can, or setting `version:` explicitly — decide
      from what the run actually reports, not in advance.
- [ ] Prove `pnpm-workspace.yaml` passes pnpm 12's new unrecognized-setting
      check. Both keys (`packages`, `minimumReleaseAgeExclude`) were verified
      recognised in 12.x from the packed release, but the *check* is new and
      hard-fails when the project pins a satisfied pnpm version — which this repo
      does.
- [ ] Correct `.github/workflows/ci.yml`'s header comment (around line 11):
      *"pnpm's own Node floor (>= 22.13) is therefore the repo's floor too"*.
      Keep the paragraph's real point — the suite needs a real install, so there
      is no no-install job — and replace the pnpm clause with the floor's actual
      basis: the oldest Node line still receiving fixes, which is also the lowest
      job in this matrix.
- [ ] Correct `scripts/workflows.test.js`'s header comment (around line 6):
      *"The floor moved to >= 22.13 because pnpm 11.11 requires it AND …"*. The
      second half — a manifest floor nobody tests is a promise nobody is keeping
      — is the half that was always load-bearing and stays verbatim.
- [ ] Add a dated Changelog line to
      `specs/complete/feat-staged-publish-pipeline/00-overview.md` recording that
      Decision 3's premise was overtaken by pnpm 12 and pointing at this spec.
      **Leave Decision 3 itself verbatim** — see overview Decision 2.
- [ ] Run the project's test command — green before the phase is done.

## Notes

**Why the correction ships in the same phase as the bump.** The bump is what
makes the comments false, so shipping them apart leaves `main` holding an
accusing check whose stated blind spot is wrong — the precise failure
`.claude/rules/negative-checks.md` §2 exists to prevent.

**`scripts/workflows.test.js` already asserts** that every manifest declares the
same floor and that `ci.yml`'s lowest matrix entry equals it. Those tests are
correct and must stay green throughout — this phase changes no manifest and no
matrix, only comments and the pnpm version.

**On the commit trailer.** The Changelog line touches a *completed* spec's file.
It resolves to **this spec's ref** — the correction is part of landing this
upgrade, not new work on that pipeline — so the bare `spec-sync ref` from this
branch is right. Stage it with an explicit pathspec like everything else.

**Record the lockfileVersion here** once observed, so phase 2 and anyone reading
later has the fact rather than the question.
