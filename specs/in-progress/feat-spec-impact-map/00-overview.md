## Problem

Generated specs are prose-heavy: to judge whether a spec has got something wrong,
a reader has to read paragraphs and reconstruct which endpoints, schemas, domain
objects, DB tables, routes and business rules the change actually touches. The
existing `> **Area:**` header is only a flat list of *files* — it doesn't name
the *behavioural surfaces* being created, changed or removed. There is no single
place on the overview to eyeball impact, so obvious mistakes (a wrong endpoint, a
schema that shouldn't change, a stray DB migration) hide in the narrative.

## Decisions

1. **Add a required `## Impact` section to `00-overview.md`.** A compact table —
   `Surface | Change | Detail` — that lists the concrete surfaces the spec
   touches. It is the scannable substitute for spelling impact out in prose, so
   the reader sees the blast radius without being told every line or file.
   *Rejected:* extending the `> **Area:**` header — a header line can't hold a
   grouped, per-surface breakdown, and Area (files) and Impact (surfaces) answer
   different questions; keep both.
2. **Table format** (`Surface | Change | Detail`). `Change` ∈ `add` / `update` /
   `remove`. Greppable and scales row-by-row. *Rejected:* one-line-per-category
   and verb-grouped bullets — both are terser but less uniform to scan and
   harder to assert on in tests.
3. **Guided-but-open surface vocabulary.** Suggest a list (Endpoint, Route/UI,
   Schema/Model, DB table/migration, Domain object, Service, CLI command, Config
   key, Skill/rule, Business rule) but do **not** enforce it — the author uses
   whatever surfaces the project actually has. *Rejected:* a fixed web taxonomy
   (UI/API/DB) — skitterspec itself is a CLI with no HTTP surface, and the
   templates ship to non-web projects.
4. **Required section, rows only for real changes.** The heading is always
   present (a consistent anchor); rows list only surfaces actually touched. A
   spec with no external surface writes a single line
   (`_No external surface changes — internal refactor only._`) instead of an
   empty table.
5. **Terse `Detail`.** Names/signatures, not sentences (`POST /orders`,
   `orders (+status col)`), reinforcing the "concise summaries" goal. The Impact
   table is derived from Phase A items 3 (Affected areas) & 5 (Data/API impact) —
   no new grilling, just a structured place to record what those already surface.
6. **Roll across the family + make it a drift target.** The section goes in the
   `/spec`, `/spec-bug` and `/spec-hotfix` overview templates, is documented in
   the `spec-planning.md` overview contract, and `/spec-review` validates the
   Impact map against real code — a stale Impact map is exactly the "obvious
   wrong place" this feature exists to surface.

## Solution overview

Each overview-template block in the skill assets gains a new section, placed
**after `## Solution overview` and before `## Phases`**:

```markdown
## Impact

Concrete surfaces this spec touches. Change: `add` · `update` · `remove`.
List only what changes; keep Detail terse (names/signatures, not prose).

| Surface | Change | Detail |
|---------|--------|--------|
| Endpoint | add | POST /orders |
| Endpoint | update | PUT /orders/:id (returns status) |
| Schema/model | add | OrderDto |
| DB | update | orders (+status col), +order_events |
| Business rule | update | totals now tax-inclusive |

_If nothing external changes: `No external surface changes — internal refactor only.`_
```

Surface is a **guided-but-open** vocabulary — suggested values (Endpoint,
Route/UI, Schema/model, DB table/migration, Domain object, Service, CLI command,
Config key, Skill/rule, Business rule) named in the template comment, but the
author writes whatever fits the project.

The source of truth is `packages/common/assets/**`; the built distributions and
the repo-local `.claude/skills/spec*` symlinks pick the change up automatically
(dist is regenerated by `node scripts/build-dist.js`, never hand-edited). Each
phase adds/extends assertions in `packages/common/test/assets.test.js` so the
section can't silently regress.
