# A `chore` spec kind, and Bugs that render as Bugs

> **Type:** Feature
> **Name:** feat-chore-kind-bug-bodies
> **Status:** In Progress — Phase 1 (started 2026-10-31)
> **Author:** Reuben Greaves
> **Developer:** Reuben Greaves
> **Raised:** 2026-10-31
> **Area:** packages/common (env/resolve.js, cli.js, assets/skills, assets/rules), packages/azure-boards, packages/github, packages/jira, packages/linear, packages/sync-core, docs/*.html
> **Stack:** worktree
> **Docs:** reference, azure-boards, github, jira, linear

## Problem

A spec is one of three kinds: `feat`, `bug` or `hotfix`. Real work also
includes **chores** — tooling, CI, dependency bumps, internal refactors no end
user sees. With no chore kind they are written as `feat-` specs and minted as
User Stories, so a consumer's release tracking walks them through
customer-facing sign-off states (live case: ereqs' `feat-azure-boards-migration`,
AB#190). Worse, a `chore-foo` folder today **silently** resolves to
`{ type: 'feat', slug: 'chore-foo' }` — a wrong answer, not a refusal.

Separately, Azure's `workItemTypeByKind` can already mint `bug → Bug`, but the
adapter only ever writes `System.Description` — a field the Agile/Scrum/CMMI
**Bug** form does not show. The body belongs in **Repro Steps**
(`Microsoft.VSTS.TCM.ReproSteps`), so every mapped Bug currently looks empty.

## Decisions

1. **Add a `chore` kind**: folder prefix `chore-`, header `> **Type:** Chore`,
   branch type `chore`, kind string `chore` everywhere (no `feat`/`feature`
   style abbreviation split for the new kind).
2. **No new entry skills.** `/spec` stays the entry point and **proposes**
   feature or chore from what grilling defined, with a one-line reason; the
   user confirms. Definition: a **chore** is anything that is not work end
   users see or functions they use within the app; everything user-facing is a
   feature. `/spec-bug` and `/spec-hotfix` are unchanged.
3. **Chore defaults**: `Gating:` defaults to `none: not user-facing` (only
   when gating is configured); `/commit` guidance maps chore specs to
   `chore`/`refactor`/`ci` commit types with no `Release-Note:`.
4. **`/no-spec` stays as it is.** The "always a ticket — mint a minimal chore
   spec" proposal was considered and declined (2026-10-31); specless work stays
   ticketless.
5. **All four providers get per-kind minting.** Azure: `workItemTypeByKind`
   gains `chore` (consumers set a custom inherited `Chore` type). GitHub and
   Linear: a new kind→label map (`labelsByKind`). Jira: a new kind→issue-type
   map (`issueTypeByKind`). Every provider falls back to its configured
   default type when a kind has no mapping, exactly as bugs do today.
6. **Azure gets a per-type body field**: `azure.bodyFieldByType`
   (e.g. `{ "Bug": "Microsoft.VSTS.TCM.ReproSteps" }`), default
   `System.Description`. Keyed by **work item type**, not spec kind, so
   `hotfix → Bug` gets Repro Steps for free. Used on all four surfaces —
   create, update, read-back, and the edited-in-Boards hash compare; a
   write-only fix would make `/spec-status` report every Bug as edited.
7. **Bug-shaped bodies are generic**, not Azure-only: a bug/hotfix spec's
   projected body leads with the bug sections (Symptom/Repro, Root cause,
   Fix) rather than the feature overview shape — a different render of the
   same `00-overview.md` sections, in `sync-core`.
8. **Unknown prefixes keep today's fallback** (`feat` + whole folder name as
   slug), with a stays-silent test per `negative-checks.md` rule 3.
9. **Branch collision accepted**: a `chore-foo` spec branches as `chore/foo`,
   the same shape `/no-spec foo` defaults to. git refuses to create an
   existing branch, so a collision is loud; not engineered around.
10. **Superset packages are not edit sites** — their `src/` is generated by
    `scripts/build-dist.js`, so every change lands in the workspace packages
    and the supersets pick it up at build.
11. **One combined spec** (user's call, 2026-10-31): the chore kind and the
    Azure bug-body work ship together.

## Solution overview

The kind vocabulary widens from three to four in the base engine
(`splitPrefix`, the spec-shaped argument check) and the authoring surfaces
(`/spec` SKILL.md, templates, `spec-planning.md`, commit guidance). Each
provider maps kinds to its idiom — work item type (Azure), label
(GitHub/Linear), issue type (Jira) — defaulting as today. Azure additionally
learns which field carries a type's body, applied symmetrically on write and
read, and `spec-sync doctor --check-remote` verifies every mapped type exists
and carries its configured body field. Consumers must add any custom types
(e.g. `Chore`) to their process before mapping them — a MIGRATION note says
so; unmapped configs keep working unchanged.
