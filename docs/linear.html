Add Linear · the superset

Opt in with one config file. Your repo stays canonical; Linear mirrors it.

The base skitterspec is tracker-free — it knows nothing about Linear. Drop a specs/.core/linear.config.json in and the sync skills wake up. No config, no Linear — every other command behaves identically.

HOW IT TALKS

Over the Linear MCP server

No API keys, no bespoke client. It rides the official hosted Linear MCP endpoint — OAuth, the same surface Claude Code already uses. The custom part is only the one-way projection on top.

HOW IT DIFFS

Against a last-pushed snapshot

Content hashes of the last push live in specs/.core/linear-base/. Each push diffs the current spec against them to send only what changed — no remote read, no merge.

HOW IT'S SAFE

The repo always wins

One direction, so nothing is ever read back or clobbered. A card moved in Linear is surfaced by /spec-status as drift and overwritten on the next push — the mirror can't fight the source.

The mapping — spec structure becomes Linear structure

→
Sub-issue bodymirrored as a read-only checklist

→
Workflow statemapped in config

The spec body travels as the issue description, each phase as a sub-issue (name, goal, state, and its task list as a read-only checklist), and the lifecycle folder sets the workflow state. Nothing is read back, so a box ticked in Linear is overwritten. Push diffs against a committed last-pushed snapshot, so only what changed is sent — IDs stamped back into the markdown.

Who owns what — no reconciliation, because there's one owner

One-way sync means there's nothing to argue about: the repo owns the spec and pushes it; Linear-native triage stays the PM's and is never touched. No base, no conflicts, no --force.

repo owns · pushed

The spec body / description, phases & tasks, completion state, and the workflow state. Authored in the repo, published up. State log, changelog & open questions stay local — never leak to Linear.

Linear-native · left alone

Priority, labels, cycles, discussion. The PM's to set in Linear; one-way sync neither pushes nor reads them, so it never fights the PM for them.

drift · surfaced, not merged

Move a card in Linear and /spec-status flags the workflow-state drift — advisory only. The repo wins on the next push; there's nothing to reconcile.

Why not just the native connector?

The plumbing is native. Keeping your repo canonical isn't.

Linear, Claude Code and Warp already talk to each other — a hosted MCP CRUD surface, an agent that codes from an assigned issue, one-shot "turn this plan into issues." Every bit of it treats Linear as the source of truth. skitterspec keeps that source in your git repo and mirrors it to Linear one way — which is the one thing none of them ship.

Set up

From no Linear at all to a linked spec.

Four steps. The only one that needs care is the API key, and the reason is that you should never paste one into a chat — including this one.

1 A team to file into

A repo maps to exactly one Linear team. If you run a team per product, that team is the product; if you run one team with a project per product, pick the team and set a default project later.

You never type a UUID by hand — step 3 discovers the teams and you pick from a list.

2 Install, and connect Linear

Install the superset or the base — never both; the superset contains the whole base.

# scaffold into .claude/ + specs/ npx @skitterbyte/skitterspec-linear init # connect Linear's own MCP server (once per machine) claude mcp add --transport http linear \ https://mcp.linear.app/mcp

A newly added server only appears in /mcp after Claude Code restarts.

3 Configure by interview

In Claude Code, run /spec-linear-setup. It reads your workspace and asks which team this repo files into, whether products split by team or by project, and which labels drive intake — then writes specs/.core/linear.config.json for you.

It also checks your workflow-state names against the workspace. That check is the one that earns its keep: Linear silently ignores an issue state it does not recognise, so a workspace that renamed Done pushes perfectly cleanly and produces a mirror that never moves.

Not using Claude Code? The CLI works standalone — see specs/.core/SETUP.md, shipped in the package. Editing the config by hand skips the state check above.

4 Your API key

With a key, descriptions go straight to Linear's API and never pass through the model. Without one everything still works over MCP — it is genuinely optional.

# run this yourself, in your own terminal skitterspec spec-sync credentials set

Never paste a key into a conversation — it enters the transcript and may be logged. The command reads it from stdin and stores it per team; it refuses to take one as an argument, because argv is visible to ps and shell history.

Already have a LINEAR_API_KEY for a different workspace? Set auth.keyEnv in your config to a repo-specific variable name, or the generic one shadows this repo's key.

Check

One command tells you whether any of that worked.

Four layers get set up by four different commands. doctor is the only thing that reports all of them at once.

skitterspec spec-sync doctor
$ skitterspec spec-sync doctor
skitterspec doctor:
scaffold ok specs/ + 16 skills installed
isolation ok env.config.json — worktree per spec
tracker ok linear.config.json — team e07c2b54… (SKS)
key missing no key for SKS
→ skitterspec spec-sync credentials set
remote skipped pass --check-remote to verify against Linear
1 check(s) need attention.

Every row that needs attention names the command that fixes it, so there is nothing to look up. A missing row is an opt-in you have not taken — reported, but it does not fail the run. Only a broken row (configured, but wrong) exits non-zero, which is what lets a skill branch on the exit code.

Add --check-remote to prove the configuration actually works, rather than merely that it parses — one call confirming the team resolves and your key is accepted:

skitterspec spec-sync doctor --check-remote
$ skitterspec spec-sync doctor --check-remote
scaffold ok specs/ + 16 skills installed
isolation ok env.config.json — worktree per spec
tracker ok linear.config.json — team e07c2b54… (SKS)
key ok …sCU8 from the environment (LINEAR_API_KEY)
remote ok team SKS resolves, key accepted
ready.

--json emits the same rows for a script. The key is only ever shown as a masked fingerprint with its source, and nothing Linear returns is echoed back — an error body can quote the request that produced it.

Fix

When a team gets renamed.

The one repair that is not obvious, because it touches three places at once.

Renaming a Linear team rewrites the key in every issue identifier — ENG-7 becomes PLT-7. Your repo stamps those identifiers in spec frontmatter, in the last-pushed snapshot filenames, and in the sub-issue keys inside those snapshots. Nothing moves them, so the next push fails with no Linear issue found for ENG-7.

skitterspec spec-sync retarget
$ skitterspec spec-sync retarget
spec-sync retarget: team fbcaaf05… (Platform)
recorded key: ENG (from config)
linear key: PLT <- renamed
would rewrite:
22 frontmatter stamp(s) (linear_identifier, linear_url, linear_issue_id)
6 base snapshot(s) (rename + re-key subIssues)
1 config key (linear.teamKey)
spot-check: PLT-7 resolves, title matches the spec
dry-run — re-run with --yes to apply.

It never takes the new key as an argument — a typo would rewrite every stamp to a key that does not exist. Instead it asks Linear for the team's current key (the team id survives a rename) and spot-checks one identifier by title before calling the plan safe: PLT-7 existing does not make it the issue that was ENG-7.

--yes applies it, refusing on a dirty tree so the rewrite lands as one reviewable, revertable change. It rewrites machine-read fields only — identifiers written in your prose are the historical record and are left exactly as they are. Nothing is pushed; your next ordinary /spec-push reconciles content now that its issues resolve again.

For everything else, doctor already names the command on the row that needs it.

Everyday

Two commands, one direction.

The repo is the source of truth. There is no pull.

/spec-status

Read-only. What the next push would create or update, whether Linear's workflow-state has drifted, and whether a phase's status markers disagree with each other. Writes nothing.

/spec-push

Repo → Linear. Diffs against the last-pushed snapshot, creates or updates the spec issue and its phase sub-issues, and stamps the returned ids back into your markdown.

/spec-sync

The repo-wide operations: what is linked, the workspace's states and projects, read-back verification, and mirroring a whole bucket at once. Run it bare for an overview.

Every lifecycle skill already refreshes the mirror as it goes, so in practice you rarely push by hand. The full list of commands lives on the base page's reference.
