The review loop

The phase ends on a page.
The page ends in a decision.

A 350-line diff read as terminal text is scrolling, not review. Every phase renders instead as a self-contained page — whole-file context that folds away, a file tree, new files included — that you read wherever you are, mark up as you go, and answer with one press. The diff never passes through the model, so the page costs zero context tokens however large it is.

What a phase hands you

Tick what you accept. Note what you don't. Press once.

Accepts, line notes and answers all travel back as one pass with your verdict already on it — nothing is retyped from memory into the conversation.

Every button is an action, not a record. Commit commits the phase with your own commit skill; Commit & Continue commits and builds the next phase — pressed from a phone, that is a whole phase built while you are away from the terminal; Request changes sends your notes straight back to be worked, and each fix returns as a resolution struck through on the next render; Discuss first reports and talks. While a note of yours is open, committing is unavailable — you asked for something, so it cannot also be fine.

Where it sits in the loop

The work happens in a worktree. You shouldn't have to go there to read it.

A phase is built on its own branch in its own checkout, so git diff in your terminal answers about the base branch. The page is rendered the moment the phase's tests go green — after the build, before the commit, which is exactly the moment a review is about.

The page ends in a decision, not a copy. Read it anywhere

Three doors to the same page — your desk, your wifi, out of the house.

Every render lists all three, labelled, in a fixed order — you pick the one that reaches you, and the engine never guesses where you are sitting.

local — the machine the run is on

http://127.0.0.1:7760/7e9e…/feat-orders

Always there. With nothing served it is a file:// page that copies the pass to your clipboard instead.

network — a phone on the same wifi

http://192.168.0.136:7760/7e9e…/feat-orders

Two doors into one room: local and network reach the same server and the same waiting run, so a press on either carries the work on. The 48-bit token in the URL is what decides who can send a pass at all.

remote — a published page, off the network

One private link per spec, updated phase after phase. A separate store, so a verdict there needs /spec-reviewed — and it stays off until you switch it on, because a published page is one this tooling cannot remove.

04 · CLAIMED

The waiting run continues

A pass that arrives while the run is watching is claimed and acted on. Outside that window, /spec-reviewed — typed by you — is the only way in.

The pass doesn't go through the model any more. A served page POSTs it to its own URL and the engine holds it, so what reaches Claude is six digits rather than kilobytes of your marks and notes. That's the same rule the diff already follows — git writes it, the engine splices it, the model never reads it — and the paste was the one place it broke. A file:// page has no server to talk to, so it still copies to your clipboard; that path isn't legacy, it's the whole story for a local reader.

The two rules that hold it together

The diff is free. A phase that ended owes an answer.

What costs, and what doesn't. The diff never passes through the model: git writes the patches and the engine splices them into the page as text. A 266KB patch costs zero context tokens, and a 289KB page costs the same to publish as a 5KB one. The only part that costs is the written review — roughly 700 output tokens, because writing it means reading the diff — so it's offered, never assumed.

A phase that ended owes an answer. The gate is armed when a phase ends and its page is rendered, and exactly two things clear it: a committing verdict, or spec-env review skip "<reason>". Until one happens /spec-next refuses to build the next phase, and a hook refuses git commit in that worktree — which is what covers a bare commit, a chained one, and your own commit skill without skitterspec editing it. Three things keep it a push rather than a wall: it is armed only by a phase ending, so reading half-finished work owes nothing; the exit is always one command, and one of them is "I am moving on" with the reason on the record; and every cannot-tell case exits 0 and says nothing. review.required: false turns it off for a project.

Design notes

Why it is shaped this way.

Every one of these was paid for — the full reasoning, kept short. Open the ones you care about.

Why does a tick survive the commit — and lapse by itself later?

A tick remembers the file, not the diff. An accept is keyed to the file's content hash, so committing the phase doesn't lapse it and neither does switching between "what changed just now" and "what this whole spec does". Change that file again and the tick lapses by itself — shown as accepted earlier — changed since, never dropped in silence. The marks are information for whoever is reading: nothing counts them, and no phase, commit or completion is gated on them.

How can the page safely carry the work on?

The phase waits for that press. /spec-next ends a phase by rendering the page and then watching, so the button is what carries the work on — there is no command to remember. It used to be true that a device reaching your page couldn't reach your conversation, and that fact was the whole guard. It isn't true any more, deliberately, and two mechanisms replaced it: the serve token — 48 random bits in the URL, minted per server, deciding who can POST at all — and the window, which decides which pass may be claimed without you naming it. A pass that arrived while the session was waiting is yours; one already sitting there when the wait began is never swept up, which is exactly the stranger's pass the old rule was written about.

What stops a pass being claimed unasked?

Outside that window, nothing is claimed unasked. Type /spec-reviewed — bare when one pass is waiting, or /spec-reviewed 324199 to name one exactly, which matters only when two are. That command is the one path the harness enforces: Claude cannot run it, so a pass picked up that way is only ever picked up because a person typed it. The rule it enforces had already been broken once by prose alone, by an agent that found a waiting approval and claimed it off disk.

Is the six-digit code a password?

The code is an address, not a password. It's printed on the page, and it couldn't gate Claude anyway — the holding area is a file Claude can read. Its one job is telling two passes apart: one waiting is claimed and acted on with nothing read back, two is a refusal to guess, and a pass you disown is dropped by its code. A code that matches nothing refuses and names nothing, never falling back to "the only one" — that fallback is exactly what would let an unread pass through. Claiming spends it, so a code works once.

Why does the button say Commit, not Approve?

The verdict names the action. It said Approve once, and an approval that only recorded itself was the one control on the page that didn't describe what it does — a review is the guard in front of an action, so the button is the action. Commit & Continue goes one step further and builds the next phase, because reading the diff on a phone is worth doing precisely when you're away from the terminal. It stops there: it never completes, lands, or tears anything down.

Why can't I commit while a note is open?

Committing is the only thing that's ever unavailable — and never because of a tally. Both committing buttons are blocked while a comment is still unresolved, for one reason you can argue with: you asked for something, so it can't also be fine. Files you never ticked block nothing — an unticked file is something you said nothing about, and a 60-file phase shouldn't be a chore before you can commit it. The verdict is one choice you make once, not a score derived from your marks, and it's consumed by the thing it asks for: a commit verdict is spent by the commit, changes by the work. So neither can go stale and later act on something nobody read. What's kept is a one-line outcome — committed a1b2c3d — shown as history the next time you open the page.

Whose commit skill runs the commit?

It commits with your commit skill, not ours. An approval hands off to whatever review.commitWith names — /commit by default, any skill you install, any skill you install. There is no off switch, deliberately: none existed and was removed, because it produced the one thing a review page must not have — a verdict that records itself and does nothing. Skitterspec never ships a copy of one: /commit belongs to skittership, where it also writes the release-note footers your changelog is built from, and a fork of it living here would drift in silence. With no such skill available it commits directly — stage, typecheck, test, conventional message — and says it took that path, every time. And if the tests fail there's no commit: approving a change judges the change, it never promises that it builds.

Where does the page live?

The page is local by default. It lands in .spec-env/reviews/<spec>.html, which is gitignored — reviewing a branch leaves no change in the branch you're reviewing. On a desktop that's the whole feature; nothing is sent anywhere.

What does publishing actually do?

Publishing is opt-in, and one page per spec. Ask, and the page becomes a private link you can open on a phone. Every later phase updates that page under a version label rather than adding another entry — so a spec is one link, not eight. It's never automatic, for one blunt reason: publishing leaves something behind that this tooling cannot remove.

Why a page instead of a terminal tab?

This is what replaced reaching for a tab. Three specs tried to solve it from the other end — one opened a viewer tab, one moved the shell into one, one reached for a better terminal program — and all three were cancelled, with their reasoning intact in specs/cancelled/ (feat-spec-diff, feat-spec-start-opens-tab, feat-lazygit-commits). The common assumption was that a terminal program must show the diff — which forces a tab, which is unreachable from a phone. Nothing about this page depends on where your shell is: the engine reads the worktree with git -C and never changes directory.
