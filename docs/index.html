Everything else is a branch off this spine. Each command sets the spec's status and moves its folder, so the repo tree is the board — no status field to keep honest by hand.

Walkthrough · ship a feature

One feature, start to finish — and exactly where each moment happens.

Follow "sort the task inbox" through the whole lifecycle. Watch the colour of the label: terminal is where you build, linear.app is where the work gets reviewed and processed.

/spec Grill the idea into a spec terminal

You describe what you want. Claude pushes back — edge cases, the data model, how you'll test it — until the shape is genuinely agreed, then writes it out as a phased folder in specs/backlog/. Nothing is coded yet; you're buying clarity first.

Optional, and the part worth adopting: push publishes the spec folder as a Linear project — and with per-item sync on, its phases as milestones and tasks as issues — stamping the returned IDs back into your markdown. Now a PM who never opens a terminal can see the plan.

Two surfaces · one source of truth

The terminal does the work. Linear.app reviews and processes it.

This is the split that's easy to miss — and the reason to bother wiring Linear in at all. You don't manage the project in either tool; you manage it in the repo, and each surface shows the slice its people need.

The coordinating surface. A projection of your specs that non-terminal people — PMs, leads, stakeholders — can read, discuss, and triage without ever cloning the repo.

/spec-push repo → Linear /spec-pull Linear → repo /spec-status what diverged

The bridge is a three-way merge, not a mirror. Push publishes structure & content; pull absorbs status, priority, labels and discussion. Neither side ever blindly clobbers the other.

Add Linear · the superset

Opt in with one config file. Then it's git-like, not a mirror.

The base skitterspec is tracker-free — it knows nothing about Linear. Drop a specs/.core/linear.config.json in and the sync skills wake up. No config, no Linear — every other command behaves identically.

HOW IT TALKS

Over the Linear MCP server

No API keys, no bespoke client. It rides the official hosted Linear MCP endpoint — OAuth, the same surface Claude Code already uses. The custom part is only the reconciler on top.

HOW IT MERGES

Three-way, with a committed base

A base snapshot lives in specs/.core/linear-base/. Every sync compares local vs remote vs base — so it can tell an edit from a conflict, and refuse to guess.

HOW IT'S SAFE

Refuses to clobber

A true conflict stops the sync unless you pass --force — which backs the losing side up first. Deletions are report-only. You never lose an edit to a background overwrite.

Default: the whole spec body travels as the project description, and the bucket sets the workflow state. Turn on per-item round-trip (sync.keyedFields) to map phases → milestones and tasks → issues individually, as shown above.

Field ownership — who wins when both sides move

Every field is tagged with an owner. That's what collapses "sync" from a scary word into a predictable one — most fields have a clear home, so most syncs have nothing to argue about.

both · co-authored

The spec body / description. Editable on either side — the only place a genuine conflict can arise, and the only place --force matters.

pull · Linear owns

Status, priority, labels, discussion. Set in Linear, flow down to the repo. The terminal never fights the PM for these.

push · repo owns

Phase & task structure, completion state. Authored in the repo, published up. State log, changelog & open questions stay local — never leak to Linear.

Why not just the native connector?

The plumbing is native. Keeping your repo canonical isn't.

Linear, Claude Code and Warp already talk to each other — a hosted MCP CRUD surface, an agent that codes from an assigned issue, one-shot "turn this plan into issues." Every bit of it treats Linear as the source of truth. skitterspec keeps that source in your git repo and reconciles to Linear — which is the one thing none of them ship.

The genuinely custom part is the three-way reconciler — the base sidecar, per-field ownership, refuse-to-clobber. Everything underneath it — the transport, OAuth, issue CRUD — is delegated to Linear's own MCP server rather than rebuilt. The two community tools that attempt file↔Linear sync (md-linear-sync, linear-md) are last-writer-wins with no base and no ownership model. This is the gap they leave open.

Get started

Two files stand between you and using the Linear layer.

You already know the terminal half. The reason you're not on Linear yet isn't complexity — it's that no one showed you it's an opt-in config, not a migration. Here it is.

1 Set up the workflow

The scaffolder writes the spec skills into .claude/ and the specs/ lifecycle folders, and wires version control. Idempotent — safe to re-run.

# scaffold into .claude/ + specs/ (this OR the base) npx @skitterbyte/skitterspec-linear init # tracker-free base instead: # npx @skitterbyte/skitterspec init # then, in Claude Code, plan something /spec add CSV export to reports

2 Wake up Linear

Add the MCP server, then drop one config file. Until it exists, every command is a plain filesystem workflow — nothing to undo.

# 1 · connect the Linear MCP server claude mcp add --transport http linear \ https://mcp.linear.app/mcp # 2 · gate the sync on one file specs/.core/linear.config.json # 3 · publish your first spec /spec-push
