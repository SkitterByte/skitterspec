Every ending

You should be able to tell what happened without reading a paragraph about it.

Every skill finishes with the same block, and says nothing while it runs beyond a question it can't answer itself or a failure at the moment it happens. The fields come from a fixed vocabulary in a fixed order, and a skill emits only the ones it declares — so two runs of the same skill are scannable against each other, and you learn where to look once.

✅ Phase 2 built — feat-orders, 2 of 4
TrackerSKS-88 · feat-orders · phase 2 moved
Branchspec/feat-orders · 3 commits, clean
BuiltPOST /orders handler, orders schema
Tests128 passed · npm test
Review7 files, +212 −18 · local 127.0.0.1:7760/… · network 192.168.0.136:7760/… · remote off
Follow-upsnone
Next/spec-next → phase 3 (Auth)

Four verdicts, and the last two are different facts about your repo: ✅ done · ⚠️ done with caveats · ❌ failed part-way, so there is a mess to clear · ⏸ refused before acting, so nothing changed. Looking for wreckage that isn't there costs as much as walking past wreckage that is. A refusal emits the block too — "nothing happened" is a reported outcome rather than an absent one.

Tracker leads because the id is how you address this work outside the repo; Next closes because it is the only row you act on. Follow-ups is always there, since a recorded none is a decision where a missing line is an oversight. And the block covers that run only — what else is in flight is a different question, and answering it here leaves you unable to tell what followed from the run you just watched. The shape is defined once, in .claude/rules/spec-reports.md, and each skill's own ## Report names only its verdicts and its fields.

The core loop

Three commands carry a feature from idea to landed.

Everything else is a branch off this spine. Each command sets the spec's status and moves its folder, so the repo tree is the board — no status field to keep honest by hand.

/spec Grill the idea into a spec terminal

You describe what you want. Claude pushes back — edge cases, the data model, how you'll test it — until the shape is genuinely agreed, then writes it out as a phased folder in specs/backlog/. Nothing is coded yet; you're buying clarity first.

Work can arrive the other way round, too: /spec SKI-188 starts from an existing Linear issue, and /spec --from-issue browses the ones your web app filed. That issue becomes the spec's issue — the reporter's thread stays where it is, and their words carry into the spec's Problem section.

Two surfaces · one source of truth

The terminal does the work. Linear.app reviews and processes it.

See the phase

The work happens in a worktree. You shouldn't have to go there to read it.

A phase is built on its own branch in its own checkout, so git diff in your terminal answers about the base branch — and a 350-line diff read as terminal text is scrolling, not review. /spec-diff renders it as a page instead: whole-file context that folds away, a file tree, new files included. You open it locally, or publish it and read it on your phone — and the page reads both ways, so what you conclude while reading comes back rather than being retyped from memory.

/spec-next

Builds the phase to green, then writes the page and tells you where it is. That happens after the tests pass and before the commit — the moment the page is about.

free · no tokens
02 · LOOK

/spec-diff

Re-renders for whatever is in front of you — half a phase, a hand edit, someone else's branch. Tick ✓ accept as you read each file, note anything against a line or the file itself. Ask for the written review and Claude adds a summary plus flag, confirm and good notes — each with a box to answer it in.

page free · review ~700 tokens
03 · HAND BACK

Your verdict

The page ends in a decision, not a copy. At the end of a phase that is ✓ Commit, ✓ Commit & Continue, ↺ Request changes and … Discuss first; a freshly written spec gets ✓ Commit & Start instead, which is the commit && /spec-start you used to type. Each carries the whole pass with its verdict already set, and on a served page it goes straight to the engine while /spec-next is still watching — so the press is the continuation. Above them sits one more line, and it isn't a verdict: ▶ Put it live commits the phase, checks it out where your dev server can see it, and hands you back the same page with the same options.

six digits · nothing else
04 · COMMIT

/commit

An approval hands off to it, so "this is fine" and the commit are one decision rather than two. You've read the phase, so the message is written from something you actually looked at rather than from memory of what you asked for.

specs/in-progress/

What costs, and what doesn't. The diff never passes through the model: git writes the patches and the engine splices them into the page as text. A 266KB patch costs zero context tokens, and a 289KB page costs the same to publish as a 5KB one. The only part that costs is the written review — roughly 700 output tokens, because writing it means reading the diff — so it's offered, never assumed.

A tick remembers the file, not the diff. An accept is keyed to the file's content hash, so committing the phase doesn't lapse it and neither does switching between "what changed just now" and "what this whole spec does". Change that file again and the tick lapses by itself — shown as accepted earlier — changed since, never dropped in silence. The marks are information for whoever is reading: nothing counts them, and no phase, commit or completion is gated on them.

The pass doesn't go through the model any more. A served page POSTs it to its own URL and the engine holds it, so what reaches Claude is six digits rather than kilobytes of your marks and notes. That's the same rule the diff already follows — git writes it, the engine splices it, the model never reads it — and the paste was the one place it broke. A file:// page has no server to talk to, so it still copies to your clipboard; that path isn't legacy, it's the whole story for a local reader.

The phase waits for that press. /spec-next ends a phase by rendering the page and then watching, so the button is what carries the work on — there is no command to remember. It used to be true that a device reaching your page couldn't reach your conversation, and that fact was the whole guard. It isn't true any more, deliberately, and two mechanisms replaced it: the serve token — 48 random bits in the URL, minted per server, deciding who can POST at all — and the window, which decides which pass may be claimed without you naming it. A pass that arrived while the session was waiting is yours; one already sitting there when the wait began is never swept up, which is exactly the stranger's pass the old rule was written about.

Outside that window, nothing is claimed unasked. Type /spec-reviewed — bare when one pass is waiting, or /spec-reviewed 324199 to name one exactly, which matters only when two are. That command is the one path the harness enforces: Claude cannot run it, so a pass picked up that way is only ever picked up because a person typed it. The rule it enforces had already been broken once by prose alone, by an agent that found a waiting approval and claimed it off disk.

The code is an address, not a password. It's printed on the page, and it couldn't gate Claude anyway — the holding area is a file Claude can read. Its one job is telling two passes apart: one waiting is claimed and acted on with nothing read back, two is a refusal to guess, and a pass you disown is dropped by its code. A code that matches nothing refuses and names nothing, never falling back to "the only one" — that fallback is exactly what would let an unread pass through. Claiming spends it, so a code works once.

The verdict names the action. It said Approve once, and an approval that only recorded itself was the one control on the page that didn't describe what it does — a review is the guard in front of an action, so the button is the action. Commit & Continue goes one step further and builds the next phase, because reading the diff on a phone is worth doing precisely when you're away from the terminal. It stops there: it never completes, lands, or tears anything down.

Committing is the only thing that's ever unavailable — and never because of a tally. Both committing buttons are blocked while a comment is still unresolved, for one reason you can argue with: you asked for something, so it can't also be fine. Files you never ticked block nothing — an unticked file is something you said nothing about, and a 60-file phase shouldn't be a chore before you can commit it. The verdict is one choice you make once, not a score derived from your marks, and it's consumed by the thing it asks for: a commit verdict is spent by the commit, changes by the work. So neither can go stale and later act on something nobody read. What's kept is a one-line outcome — committed a1b2c3d — shown as history the next time you open the page.

It commits with your commit skill, not ours. An approval hands off to whatever review.commitWith names — /commit by default, any skill you install, any skill you install. There is no off switch, deliberately: none existed and was removed, because it produced the one thing a review page must not have — a verdict that records itself and does nothing. Skitterspec never ships a copy of one: /commit belongs to skittership, where it also writes the release-note footers your changelog is built from, and a fork of it living here would drift in silence. With no such skill available it commits directly — stage, typecheck, test, conventional message — and says it took that path, every time. And if the tests fail there's no commit: approving a change judges the change, it never promises that it builds.

A phase that ended owes an answer. The gate is armed when a phase ends and its page is rendered, and exactly two things clear it: a committing verdict, or spec-env review skip "<reason>". Until one happens /spec-next refuses to build the next phase, and a hook refuses git commit in that worktree — which is what covers a bare commit, a chained one, and your own commit skill without skitterspec editing it. Three things keep it a push rather than a wall: it is armed only by a phase ending, so reading half-finished work owes nothing; the exit is always one command, and one of them is "I am moving on" with the reason on the record; and every cannot-tell case exits 0 and says nothing. review.required: false turns it off for a project.

Every render lists where the page can be read — labelled, in a fixed order, so you pick the one that reaches you instead of the engine guessing. It guessed for a while, and got it wrong three different ways in one day. local and network are two doors into one room: the same server and the same waiting verdict, so a press on either wakes the same run. remote is a published page, a separate store — a verdict there needs /spec-reviewed, and it stays off until you type /spec-remote-review, because publishing leaves a page this tooling cannot remove. A fourth line, live, answers the other way to judge a change: whether it is also running, and what to type to change that.

The page is local by default. It lands in .spec-env/reviews/<spec>.html, which is gitignored — reviewing a branch leaves no change in the branch you're reviewing. On a desktop that's the whole feature; nothing is sent anywhere.

Publishing is opt-in, and one page per spec. Ask, and the page becomes a private link you can open on a phone. Every later phase updates that page under a version label rather than adding another entry — so a spec is one link, not eight. It's never automatic, for one blunt reason: publishing leaves something behind that this tooling cannot remove.

This is what replaced reaching for a tab. Three specs tried to solve it from the other end — one opened a viewer tab, one moved the shell into one, one reached for a better terminal program — and all three were cancelled, with their reasoning intact in specs/cancelled/ (feat-spec-diff, feat-spec-start-opens-tab, feat-lazygit-commits). The common assumption was that a terminal program must show the diff — which forces a tab, which is unreachable from a phone. Nothing about this page depends on where your shell is: the engine reads the worktree with git -C and never changes directory.

# the uncommitted work — what this phase just did $ skitterspec spec-env review spec-env review: feat-phase-review (uncommitted) 9 files, +839 -24 page: /repo/.spec-env/reviews/feat-phase-review.html # or everything since the base branch — the whole spec $ skitterspec spec-env review --branch
Under the skills

The engine the skills drive — and the bits you drive yourself.

skitterspec spec-env is the per-spec isolation engine: worktrees, dev servers, the proxy, landing, teardown. Most of its verbs are planners — they print commands and create nothing, and a skill runs what they print. Reach for them directly only when you want to see the plan, or for the three at the bottom that have no skill in front of them.

The spec name is optional, everywhere. Omit it and the engine uses the worktree you are standing in — so inside a spec's worktree, every verb above just works. From the primary checkout with several worktrees open it lists them and stops, rather than guessing. connect and live used to be the two exceptions, where a missing spec meant main; they aren't any more, and main is how you hand either one back.

# from inside a spec's worktree $ skitterspec spec-env resolve spec: feat-cli-engine-docs (backlog) type/slug: feat / cli-engine-docs branch: feat/cli-engine-docs worktree: /Users/you/code/skitterspec-wt/cli-engine-docs project: skitterspec_cli-engine-docs # nothing to reap, and it says what it protected $ skitterspec spec-env prune spec-env prune: no orphaned volumes in skitterspec_* (0 namespace volume(s), 1 live spec(s) protected).

What status counts. A spec is provisioned when it has a worktree — so every in-flight spec appears, whether or not it runs Docker. Specs that do get a slot and a port block shown beside them; the rest just show their worktree path.

Get started

One command scaffolds it. Nothing else is required.

The base is tracker-free and stays that way. No account, no config, no service — your specs are markdown in your repo, and every command is a filesystem operation.

1 Scaffold it

Writes the spec skills and slash commands into .claude/, the specs/ lifecycle folders, and the rules they follow. Idempotent — safe to re-run, and it repairs a half-install rather than clobbering your edits.

# tracker-free base npx @skitterbyte/skitterspec init # or the Linear superset instead — one OR the other, # never both; the superset contains the whole base # npx @skitterbyte/skitterspec-linear init

2 Plan something

In Claude Code. /spec grills you to a shared understanding first, then writes a phased spec into specs/backlog/ — it does not start coding.

/spec add CSV export to reports # then build it, phase by phase /spec-start feat-csv-export # verify, land, tear down /spec-complete

3 Where things live

A spec's folder is its status — there is no index to keep in step, and git log is the history.

specs/ backlog/ ready to build in-progress/ being built now complete/ done cancelled/ dropped, with a reason .core/ rules + config

Git does not store empty folders, so a bucket disappears when nothing is in it and returns when something is. That is normal.

4 Optional: a worktree per spec

Turn on per-spec isolation and /spec-start gives every in-progress spec its own git worktree and branch. Several specs run side by side without stashing, and main stays free.

npx @skitterbyte/skitterspec init --isolation

Teardown is folded into /spec-complete and /spec-cancel, so finishing a spec reclaims its worktree.

5 Optional: did we decide about a flag?

A spec can reach /spec-complete having never been asked whether it ships behind a feature flag — and “nobody asked” looks exactly like “we decided not to”. Turn on release gating and every spec records the answer on its own header.

npx @skitterbyte/skitterspec init --gating
> **Gating:** search-ranking-v2 > **Gating:** none: additive, nothing to revert

A flag name, or a reason for not using one — the reason is the point, because a missing line is an oversight and a reason is a decision. Skitterspec never reads your flag system; it asks the question and cites your documentation. gating check lists specs with no answer and always exits 0, so it never blocks your work.
