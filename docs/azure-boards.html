Set it up. Prove it works.

The Azure Boards superset is the base plus one-way sync to Azure DevOps work items. Everything below is opt-in: until specs/.core/azure-boards.config.json exists, every command is a plain filesystem workflow. New here? Start with the base. Your tracker is Linear, Jira or GitHub? Each superset has its own page.

Add Azure Boards · the superset

Opt in with one config file. Your repo stays canonical; Boards mirrors it.

The base skitterspec is tracker-free — it knows nothing about Azure. Drop a specs/.core/azure-boards.config.json in and the sync skills wake up. No config, no Azure — every other command behaves identically.

HOW IT TALKS

A PAT, or Microsoft's MCP server

With a Personal Access Token set, the engine calls the Azure DevOps REST API directly and descriptions never pass through the model. Without it, sync rides Microsoft's official MCP server — and even then the engine itself never calls an MCP tool: the skill fetches and hands files to the engine.

HOW IT DIFFS

Against a last-pushed snapshot

Content hashes of the last push live in specs/.core/azure-base/. Each push diffs the current spec against them to send only what changed — no remote read, no merge.

HOW IT'S SAFE

The repo always wins

One direction, so nothing is ever read back or clobbered. Skitterspec tells Boards about its own transitions and nothing else, so a state someone moves there is left alone. A description edited there is reported loudly before the next push overwrites it. The mirror can't fight the source.

The mapping — spec structure becomes Boards structure

spec folder specs/<bucket>/feat-name/
→
Work itemthe whole spec, one item — AB#123
phase file 01-schema.md, 02-controls.md …
→
Child itemone per phase, under a parent/child link
task checkbox - [ ] add sortBy param
→
Markdown checklistrenders natively in the child — a read-only mirror
lifecycle bucket backlog / in-progress / complete
→
Statewritten directly, mapped in config, validated up front

Boards stores a markdown-format description verbatim — the adapter declares the format beside the field, so a read-back is normally the pushed text byte for byte, task checkboxes render natively, and verification compares words only where an HTML-era item (one created in the Boards UI) reduces to text first. A field saved as markdown cannot revert to HTML — Azure's rule, and fine one-way: this provider never writes HTML. Push diffs against a committed last-pushed snapshot, so only what changed is sent — item ids stamped back into the markdown.

There is no project picker, on purpose. azure.project pins exactly one project per repo, and every spec item lands there by construction (azure.areaPath places it inside the project when a team wants one). The question the config asks is not "which project do you like" — it is "which product's work does this repo hold", and it is answered once.

Who owns what — no reconciliation, because there's one owner

One-way sync means there's nothing to argue about: the repo owns the spec and pushes it; Boards-native triage stays the PM's and is never touched. No base, no conflicts, no --force.

repo owns · pushed

The spec body / description, phases & tasks, completion state, the work item state, and the assignee. Authored in the repo, published up. State log, changelog & open questions stay local — never leak to Boards.

Boards-native · left alone

Priority, iterations, area moves, tags, discussion. The PM's to set in Boards; one-way sync neither pushes nor reads them, so it never fights the PM for them.

edits · surfaced, not merged

Edit an item's description in Boards and /spec-status says so before the next push replaces it. A moved item is never reported — skitterspec doesn't read state back, so there's nothing to reconcile.

How a state moves

By direct write — validated before anything else is.

Boards' work item types and states are process-defined — Basic has Issue/Task with To Do/Doing/Done, Agile has User Story/Task with New/Active/Closed, a custom process has whatever it has. So the config names the types and the bucket→state map, and the engine validates every name against the process before the first write: Azure refuses an unknown state only at write time, after the description has already landed, so an unchecked push would half-apply.

The mapping lives in config: states names the Boards state for each lifecycle bucket — To Do / Doing / Done by default (the Basic process's), with cancelled also defaulting to Done, because Basic carries no Cancelled state. Validation runs against the union of both configured types' states, since one map serves the spec item and its children and the two types can differ.

skitterspec-azure-boards spec-sync plan
$ skitterspec-azure-boards spec-sync plan feat-orders --workspace-states states.json
spec-sync plan: refusing — configured state name(s) not in the project
states.complete: "Shipped" is not a state these types have
use "Done" instead
available: To Do, Doing, Done
Fix specs/.core/azure-boards.config.json -> states.

That is the --workspace-states idiom: plan refuses to run until the configured names have been checked against the types' real ones (skitterspec-azure-boards spec-sync states --json prints exactly the array it wants). /spec-push does the fetch for you, so nothing changes if you drive sync through the skill; a script calling the CLI directly passes the file itself.

Set up

From no Azure at all to a linked spec.

Four steps. The only one that needs care is the PAT, and the reason is that you should never paste one into a chat — including this one.

1 A project to land in

A repo maps to exactly one Azure DevOps project. Every spec item is created there by construction; there is no per-spec picker to answer later, which is why the question is worth a moment now: it isn't "which project do you like", it's which product's work does this repo hold.

Specs mint as the Issue type and phases as Task by default — the Basic process's names, both configurable, because an Agile or custom process spells them differently.

2 Install the superset

Install this superset or the base — never both; the superset contains the whole base (and exposes the skitterspec binary name alongside its own).

# scaffold into .claude/ + specs/ npx @skitterbyte/skitterspec-azure-boards init

Connecting Microsoft's MCP server is optional: with a PAT set (step 3) the engine talks to Azure DevOps directly and MCP is never consulted. Without it, the sync skills ride the MCP server instead — the engine itself still makes no MCP call.

3 Your credentials

Azure DevOps authenticates with a Personal Access Token, created in Azure DevOps under User settings → Personal access tokens, scoped Work Items (Read & Write) — add Identity (Read) if you want user search.

# run this yourself, in your own terminal skitterspec-azure-boards spec-sync credentials set

It prompts for the token hidden, then stores it per org, outside the repo. It refuses to take a token as an argument, because argv is visible to ps and shell history — and never paste one into a conversation: it enters the transcript and may be logged.

Prefer the environment? AZURE_DEVOPS_EXT_PAT works as-is — the official CLI's variable, so a machine set up for az boards needs nothing new; auth.tokenEnv renames it per repo.

4 Configure by interview

In Claude Code, run /spec-azure-setup. It asks for the org URL and project, confirms the work item types, and settles the bucket→state mapping — then hands the answers to the engine, which validates and writes specs/.core/azure-boards.config.json.

It checks your state names against the process before writing. That check is the one that earns its keep: Azure refuses an unknown state only at write time, after the description already landed — so a name your process lacks is caught here, in the setup conversation, rather than half-way through your first push.

Not using Claude Code? The CLI works standalone — see specs/.core/SETUP.md, shipped in the package. Editing the config by hand skips the check above; /spec-push catches it at your first push instead.

Check

One command tells you whether any of that worked.

The config, the PAT and the process's states get set up by different commands. doctor is the only thing that reports all of them at once.

skitterspec-azure-boards spec-sync doctor
$ skitterspec-azure-boards spec-sync doctor
spec-sync doctor:
ok Azure config: spike @ https://dev.azure.com/acme
-- Credentials: no Azure DevOps credentials: set AZURE_DEVOPS_EXT_PAT, or run `skitterspec-azure-boards spec-sync credentials set`
fix: skitterspec-azure-boards spec-sync credentials set

Every row that needs attention names the command that fixes it, so there is nothing to look up. A -- (missing) row is an opt-in you have not taken — reported, but it does not fail the run. Only an XX (broken) row — configured, but wrong — exits non-zero, which is what lets a skill branch on the exit code.

Add --check-remote to prove the configuration actually works, rather than merely that it parses — one call confirming the org answers, the PAT is accepted, every configured state really exists on the types, and whether the PAT can search identities:

skitterspec-azure-boards spec-sync doctor --check-remote
$ skitterspec-azure-boards spec-sync doctor --check-remote
spec-sync doctor:
ok Azure config: spike @ https://dev.azure.com/acme
ok Credentials: PAT …f2c9 (store)
ok Azure reachable: as Jane Dev
ok State names: every configured state exists
!! Identity search: PAT lacks Identity (Read) — user search degrades; whoami and assignment still work

--json emits the same rows for a script. The PAT is only ever shown as a masked fingerprint with its source, and it never appears in an error — a refusal names what was looked for and where, not what was found. The identity row is a warn, never broken: work item sync is whole without the scope; only users search degrades.

Everyday

Two commands, one direction.

The repo is the source of truth. There is no pull.

/spec-status

Read-only. What the next push would create or update, and whether someone edited the item's description over there, which the next push will replace. Writes nothing.

/spec-push

Repo → Boards. Fetches the types' states, diffs against the last-pushed snapshot, creates or updates the spec item and its phase children, and stamps the returned ids back into your markdown.

/spec-sync

The repo-wide operations: what is linked, the types' states, read-back verification, and mirroring a whole bucket at once. Run it bare for an overview.

/spec-list

What the project holds, read-only — id, title, state, and each spec's folder name so /spec-start <name> is a paste away. The folder buckets are only the truth on the branch you are standing on; this answers from the mirror instead.

/spec-claim

Take a spec, hand it back, or hand it to a teammate — the spec records who is building it and the work item is assigned to them. Identity derives from the PAT (spec-sync whoami) and is cached per org.

/spec-azure-setup

The setup interview — which org, which project, which states mean which bucket here — then it hands the answers to the engine, which validates them against the process and writes azure-boards.config.json.

Every lifecycle skill already refreshes the mirror as it goes, so in practice you rarely push by hand. These six are what the superset adds; the base's own fifteen — the lifecycle, the review loop, isolation — are listed on the base page, and installing this package gives you all of them.

Releases and deploys are yours to record. Skitterspec answers one release question — which tickets a range contains — with spec-sync released <range> --json, each row carrying its spec and url. Your pipeline pipes that into the Azure CLI or REST API to set whatever field, tag or work item your process uses.

Not yet shipped for Azure Boards (the Linear provider has them): retarget, reattach, and the sanitise pass. The engine's own usage text says so too, so the CLI and this page cannot disagree about it.

Under the skills

Every spec-sync verb, and who runs it.

Most of these are plumbing that /spec-push and /spec-status drive for you — listed so you can read a plan or debug a mirror, not so you type them. Several providers ship an engine with this name, so the rows write it as spec-sync (azure) to say whose table this is; the CLI is a local devDependency and never on PATH, so every verb is reached as pnpm exec skitterspec-azure-boards spec-sync ….

# what ticket does this commit belong to? (the commit-trailer rule uses this) $ pnpm exec skitterspec-azure-boards spec-sync ref AB#58 # what shipped since the last release tag $ pnpm exec skitterspec-azure-boards spec-sync released v1.8.0..HEAD spec-sync released: v1.8.0..HEAD — 14 commit(s) AB#58 (6 commit(s)) AB#55 (4 commit(s)) 1 commit(s) carry no Refs: trailer 1 commit(s) reference an earlier tracker 2 bookkeeping commit(s) ignored

Three of these are honest about having nothing to say. ref exits non-zero and prints nothing on a commit with no ticket — on main, or a spec kept deliberately local — so a trailer is omitted rather than invented. released counts unreferenced commits rather than hiding them, and a repo migrated off Linear or Jira sees its old trailers counted as historical rather than accused of missing a ref.
